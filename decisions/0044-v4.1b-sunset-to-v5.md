# ADR-0044: V4.1-B → V5 sunset (withdraw-only, no forced migration)

**Status:** Accepted 2026-07-07 (PM call, operator-delegated). Fills in the "real consolidation at V5" that [[0041-single-vault-consolidation]] deferred.

## Context
At V5 (TWAB) mainnet launch, the existing production vault is **V4.1-B** (round-based `TicketPrizePool`, the surviving vault after ADR-0041 retired V4.1-A into it). It holds real user principal. We must decide what happens to V4.1-B and its depositors when V5 becomes the product on everdraw.xyz. ADR-0041 said consolidation happens "at V5" but did not specify the mechanism.

## Decision
**Sunset V4.1-B by making it withdraw-only; do NOT force-migrate funds. Users move to V5 themselves; nudge them with V5 points.**

Concretely:
1. **Stop new V4.1-B deposits at cutover.** Do not open a new V4.1-B round after the launch cutover; let the final in-flight round settle and pay out normally (never strand a round mid-cycle).
2. **Withdrawals stay live indefinitely.** V4.1-B principal is always withdrawable — that guarantee is never broken by the sunset.
3. **No forced/programmatic migration.** We never move a user's funds without their action. Users withdraw from V4.1-B and deposit into V5 when they choose.
4. **Frontend:** V5 becomes the default vault on everdraw.xyz; V4.1-B is reachable via the existing "Previous Vault" path with a clear "withdraw & move to V5" prompt for anyone still holding a V4.1-B position.
5. **Migration nudge via points (not cash):** count a first V5 deposit by a wallet that held V4.1-B as eligible for a one-time migration points bonus, reusing the V5 points system. Keeps points' value ambiguous (no cash incentive, consistent with the standing rule) while still rewarding the move. (Exact bonus TBD; not load-bearing for the sunset.)
6. **Retire the V4.1-B keeper** only after the final round settles and a defined withdrawal window has elapsed — then decommission that keeper/monitoring.

## Rationale
- **Custody & security:** you cannot (and should not) move user funds they did not authorize. A programmatic cross-contract migration is a large, fund-touching, audit-heavy surface — exactly what you do NOT want to introduce in the same window as a brand-new mechanism launch.
- **Precedent:** ADR-0041 already did precisely this for V4.1-A → B (withdraw-only, no forced migration). Reusing a proven, understood playbook.
- **Focus:** a parallel indefinite run splits liquidity, doubles keeper/indexer/monitoring/ops burden, and confuses UX (two live products). The sunset concentrates everything on V5.
- **The withdraw path already exists** in the frontend ("Previous Vault"), so cutover is a config/UX change, not new fund-handling code.

## Rejected alternatives
- **Forced/programmatic migration** — moves user funds without authorization (custody + security risk), needs a bespoke migration contract + audit, and V4.1-B principal is round-locked so it can't simply be yanked. Rejected.
- **Indefinite parallel run** — splits liquidity, doubles ops, confuses UX, keeps the old V4 stack alive forever. Rejected.

## External dependencies (rule #5)
- **V4.1-B contract:** must support "no new rounds / withdrawals live" cleanly (the withdraw-live-after-stop behavior already exists in V4). Confirm the exact call to stop opening rounds.
- **Frontend:** V5 default + V4.1-B behind "Previous Vault" with the migration prompt (production Vercel project cutover — see the launch checklist).
- **Indexer:** must keep serving V4.1-B history/withdraw state during the sunset window (don't drop the old pool from indexing until it's fully drained).
- **Keeper/monitoring:** V4.1-B keeper runs until final settlement, then is retired — coordinate so it isn't shut off with a round in flight.
